# Research: Multi-Company BHI Enrollment and Monthly Billing on One Shared Database

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-09-29

This replaces the earlier per-company-schema research. Each decision resolves an unknown from the plan's Technical Context. File references point to the current codebase.

---

## R1. Where the 18 BHI tables live

**Decision**: one dedicated PostgreSQL schema, `bhi`, shared by all companies. Drizzle declares it with `pgSchema("bhi")`. Platform tables stay in `public`. At sign-off, the four retired shared tables (`companies`, `employee_members`, `dependents`, `beneficiaries`) move to a `legacy` schema.

**Rationale**:
- The client wants "one physical DB, with logically segregated data" (FR-001). One schema for every company meets that.
- A separate `bhi` schema keeps the client's tables apart from the application's platform tables and from the old tables during migration. `bhi.member` and `public.employee_members` can live side by side until cut-over.
- The schema name is fixed, so `pgSchema` works at compile time. This was the problem with per-company schemas.
- `class` is a non-reserved keyword in PostgreSQL, so it is valid as a table name. Drizzle quotes identifiers anyway.

**Alternatives considered**:
- Tables directly in `public`: rejected. It mixes client and platform tables, and would clash if the Access names are ever pluralised.
- One schema per company: replaced on 2026-09-29 by the client requirement.

## R2. Naming style

**Decision**: snake_case, derived from the Access names by one rule. Split at lower-to-upper case boundaries, and keep `ID` and `SHA256` as whole words. So `MemberID` becomes `member_id`, `IDType` becomes `id_type`, and `InventoryCellSHA256` becomes `inventory_cell_sha256`. Table names use the same rule: `premium_rates`, `billing_line`, `import_exception`.

**Rationale**: matches the existing codebase and avoids quoting identifiers. The full map is [contracts/bhi-schema.sql](contracts/bhi-schema.sql). A script checked all 18 tables and 223 Access columns against the spec's Key Entities, plus the D1 deviation column: 0 differences.

## R4. How segregation is enforced (FR-010, FR-011, FR-015)

**Decision**: two layers.

1. **In code.** Every request resolves a scope from the admin's role:
   - `ALL` for super admin, support and auditor.
   - `GROUP(id)` for a group admin.
   - `COMPANY(number)` for client admins and HR administrators.

   Routes filter by the companies in that scope and check writes against it, much as `lib/adminScope.ts` does today.

2. **In the database.** PostgreSQL row-level security (RLS) is enabled and `FORCE`d on every `bhi` table. Each scoped unit of work runs in a transaction that first runs:
   ```sql
   SELECT set_config('bhi.companies', '<comma list>', true),
          set_config('bhi.all', '<on|off>', true)
   ```
   Policies allow a row only when its company is in `bhi.companies`, or `bhi.all = on`. A query that runs without these settings sees **no rows**, so a forgotten filter fails closed (FR-011).

**How each table's company is found** (FR-009):

| Tables | Company from |
|---|---|
| company, member, billing_run, billing_line, company_billing_rule | their own `company_number` |
| premium_rates | `company_number`. A blank value is a standard rate, visible to everyone. |
| class | shared reference data, visible to everyone |
| dependent, beneficiary | `EXISTS` on `member` with the same `member_id` |
| enrollment_status_history | `company_number` when set, otherwise `member_id`, then member |
| source_workbook_archive/sheet, raw_enrollment_row/cell | `source_ordinal`, then `public.import_batch` |
| import_exception, import_adjustment | `source_file`, then `public.import_batch` |
| import_reconciliation, import_documentation | their ID, then `public.import_batch_record` |

- Write policies (`WITH CHECK`) apply the same rule, so a company-scoped user cannot insert a row for another company.
- Changing classes and standard rates needs `bhi.all = on`. The permission check makes that true only for super admins (FR-021, FR-025).

**Rationale**: the spec requires segregation not to depend on every query remembering its filter (FR-011, SC-003). RLS gives a second, independent guard in the database the client wants to share.

**Important**: RLS does not apply to superusers, and applies to the table owner only because of `FORCE`. The API must therefore run as `bhi_app` (R5). Tests must also run as `bhi_app`, never as `postgres`.

**Alternatives considered**:
- Code-only filtering: rejected, because it fails FR-011.
- Views per company: rejected, because they must be rebuilt at every onboarding.

## R5. Database roles and grants

**Decision**:

| Role | Used by | Rights |
|---|---|---|
| `bhi_owner` | SQL migrations in `deploy/db/migrations/`, the legacy migration command | Owns `bhi`, `public` and `legacy`; runs DDL |
| `bhi_app` | The API (`DATABASE_URL`) | `bhi.*`: SELECT, INSERT, UPDATE, **no DELETE**. `public.audit_logs`: SELECT and INSERT only. Other `public` tables: as today. `legacy.*`: SELECT only. |

- Deployments get a second connection string, `DATABASE_OWNER_URL`, used only by the migration runners.
- Locally, `setup-local.ps1` creates both roles. The existing `bhi_user` becomes `bhi_app`.

**Rationale**:
- Principle III requires no hard-delete path and an audit store written by credentials with no update or delete rights. Grants enforce that in the database.
- It also makes the R3 cascade (BillingRun to BillingLine) unreachable from the application.

## R6. How structural changes are applied

**Decision**: keep the project's existing way.
- Hand-written SQL migrations that are safe to re-run, numbered in `deploy/db/migrations/` and applied in order by `setup-local.ps1`, `docker/migrate/apply-migrations.sh` and `deploy/azure/03-migrate-db.ps1`, now as `bhi_owner`.
- Drizzle table definitions in `lib/db/src/schema/bhi/` mirror the SQL for typed queries.
- The SC-001 structural test checks that the live database matches [contracts/bhi-schema.sql](contracts/bhi-schema.sql).
- `drizzle-kit push` stays a development convenience only. It must not run against a database with RLS policies it does not model, so `drizzle.config.ts` gets `schemaFilter: ["public"]`.

**Rationale**: one schema means a normal migration applies to every company at once. The per-company upgrade runner is no longer needed.

## R7. Uniqueness rules

- **Member, `(id_type, id_number)` unique across the platform** (FR-007): the Access unique key applies as given, because all companies share one table.
  - Adding a person who exists in another company fails on this key.
  - The API maps that failure to `409 ID_ALREADY_REGISTERED` with the message "This ID is already registered on the platform. Contact NALICO." It does not name the other company.
  - The database checks uniqueness across all rows whatever RLS hides, so the rule holds even though the user cannot see the other row.
- **PremiumRates, `(company_number, class_code, coverage_band, effective_date)`** (D2) uses `UNIQUE NULLS NOT DISTINCT`, so two standard rates for the same class, tier and date cannot coexist. This needs PostgreSQL 15 or newer. The project uses 16 (`compose.yaml`, `.replit`), and the local host install is 15.

## R8. Client groups and roles (FR-012 to FR-014, FR-018)

**Decision**:
- New platform table `public.client_groups (id, name, active)`.
- New platform table `public.client_group_companies (group_id, company_number unique)`. A company belongs to at most one group.
- `admin_users` gains `group_scope uuid`, referencing `client_groups`.
- Scope rules:

| Role (stored value) | Shown as | Scope column | Rule |
|---|---|---|---|
| `ROLE_PLATFORM_ADMIN` | Super admin | none | All companies, read and write. At least one must stay active (the existing `lastAdmin.ts` rule). |
| `ROLE_HR_GROUP_ADMIN` | Group admin | `group_scope` required | The group's companies, with client admin rights in each |
| `ROLE_CLIENT_ADMIN` (new) | Client admin | `company_scope` required | One company. Manages that company's users. At least one active per company. |
| `ROLE_HR_ADMIN` | HR administrator | `company_scope` required | One company |
| `ROLE_SUPPORT`, `ROLE_AUDITOR` | Support, Auditor | none | All companies, read-only (permission sets unchanged) |

- The stored role values stay the same, so existing sessions and audit rows remain valid. Only the display label changes.
- **User management scope**:
  - A client admin can grant `ROLE_CLIENT_ADMIN` or `ROLE_HR_ADMIN` for its own company only.
  - A group admin can do the same for any company in its group.
  - Only a super admin can create super admin, group admin, support or auditor users.
- **New permissions**:
  - `CLASS_MANAGE`, `RATE_MANAGE` and `BILLING_MANAGE`: super admin only.
  - `BILLING_READ`: super admin, group admin, client admin, auditor.
  - `ADMIN_USER_MANAGE` is added to client admin, and is now always scope-checked.
- **Migration**: the six Beharry companies form the group "Beharry". Existing `ROLE_HR_GROUP_ADMIN` users (null scope today) get `group_scope` set to that group.

## R9. How platform tables refer to BHI records (FR-043)

**Decision**:
- `card_sessions`, `change_requests`, `policy_memberships` and `verification_sessions` gain `member_ref integer`, a real foreign key to `bhi.member(member_id)`.
- `change_requests` also gains `dependent_ref integer`, a foreign key to `bhi.dependent`.
- The legacy migration writes `public.legacy_key_map (legacy_uuid, entity_type, new_id, exception_id)` and fills the new columns from it.
- Old UUID columns become nullable and are dropped at sign-off (R18).
- `audit_logs` is never rewritten. Old UUIDs are translated through the map when history is displayed.

**Rationale**: in one database, real foreign keys are possible again. Keeping the old columns until sign-off keeps rollback possible.

## R10. Employee card lookup across companies (FR-016)

**Decision**: the same behaviour as agreed on 2026-09-29, now as a single query.

1. `POST /v1/lookup` runs in `ALL` scope and matches `bhi.member` by email or phone (loose phone match from `lib/phone.ts`), counting only `active = true` members of active companies.
2. It always creates one verification session, storing `matched_members jsonb`, and always returns `200 CODE_SENT` with a masked destination. The pre-verification `404 NOT_FOUND`, `SELECT` and `503` replies are removed.
3. The code goes to each distinct stored contact of the matches, never to the typed value. Delivery runs after the response is sent, and the response is held to an 800 ms floor.
4. `POST /v1/otp/verify`, after a correct code, decides:
   - One member: `CARD`.
   - Several members in one company: `SELECT`, with the existing non-identifying labels, then `POST /v1/otp/select`.
   - Two or more companies: `MULTI_COMPANY`, with the fixed message and no card. A `public.lookup_alerts` row is written.

Details are in [contracts/employee-lookup.md](contracts/employee-lookup.md). With FR-007, the same person cannot be in two companies, so a multi-company match now only happens when two different people share an email or phone.

## R11. Billing: what "as at the start of the month" means (FR-029, FR-033)

**Decision**: a change takes effect for billing from the **time it is recorded in the system**, not from a date someone types in. The bill for month M uses the state at `T = 00:00 on the 1st of M, Guyana time (UTC−4)`.

- A member is billed in M if:
  - `member.created_at < T`, and
  - the member was active at T. The latest `enrollment_status_history` row for the member with `changed_at < T` decides; if there is none, the member's creation state decides.
- The member's class at T comes from a new platform table, `public.member_class_history (member_id, class_code, recorded_at, recorded_by)`. It gets one row at creation and one per class change. The class at T is the latest row with `recorded_at < T`.
- Active dependents at T: dependents with `created_at < T` that were active at T, using their `enrollment_status_history` rows the same way. Every dependent counts as 1, whatever the relationship (FR-023).
- Tier = min(count, 3). This is `dependent_band`, which gives the coverage band (FR-022).

**Rationale**:
- "Additions and removals take effect from the start of the next month" (client). Using the recorded time means a bill generated late (for example on the 5th) is still correct. It also stops backdated entries from changing a past month.
- The Access model has no class history. EnrollmentStatusHistory covers only active/inactive, and its OldActive/NewActive columns cannot hold a class, so class history is kept at platform level (spec rule: tables not in the model are kept as separate platform tables).

**Consequence**: every Active change for a member, dependent or beneficiary **must** write `enrollment_status_history`. The table's `changed_at` becomes load-bearing for billing. The migration writes one row for every inactive record, and one "created" row for every class.

**Alternatives considered**:
- A snapshot job at 00:00 on the 1st: rejected. If it runs late or fails, the month is priced wrongly with no way to recover.
- Declared effective dates (PlanDate, InactiveDate): rejected. They are optional in the model and can be backdated.

## R12. Billing: choosing the rate and the split (FR-031, FR-032)

**Rate for a member line**, with `T` as in R11:

```text
rate = premium_rates where class_code = <class at T> and dependent_band = <tier>
         and active and effective_date <= date(T)
         and company_number = <company>          -- company rate first
       order by effective_date desc limit 1
   else the same query with company_number is null   -- standard rate
```

**Split**:
- If an active `company_billing_rule` for the company has `effective_date <= date(T)`, take the latest one: `company_premium = round(total × company_share_percent / 100, 2)` and `employee_premium = total − company_premium`.
- Otherwise use the rate's own `company_premium` and `employee_premium`.

This follows the spec assumption; **confirm with the client**.

**Unpriced members**: if no rate is found, the member goes into `public.billing_run_issues (billing_run_id, member_id, reason)` instead of a line. A run with issues cannot be finalised (FR-034). BillingLine requires every premium column, so an unpriced line cannot be written.

## R13. Billing runs and recalculation (FR-028, FR-033, FR-034)

**Decision**:
- `billing_run.status` takes `DRAFT`, `FINAL` or `SUPERSEDED`.
- One non-superseded run per company and month. The BHI index on `(company_number, billing_month)` is not unique, so this is enforced in code under an advisory lock on `(company_number, month)`. Adding a unique index would be a further deviation.
- **Recalculation creates a new DRAFT run and marks the old draft `SUPERSEDED`.** Nothing is deleted, and `bhi_app` has no DELETE right.
- **FINAL** runs and their lines are never updated. A trigger on `billing_run` and `billing_line` rejects any update to a FINAL run or its lines.
- **What triggers recalculation**: any change recorded before T of a month whose run is still DRAFT. In practice this means:
  - a draft generated early as a preview;
  - a rate added with `effective_date <= date(T)` after the draft was made.

  Member, class and dependent changes recorded after T belong to the next month by R11, so they never change month M. They are picked up automatically when M+1 is generated. This is the client's "class change plus new dependent triggers recalculation, across all customers".
- **Generating**: super admins generate one company or all companies (`ALL` scope). Each company is generated in its own transaction.
- **Performance target**: about 5,000 members in under 5 minutes (SC-011). The design uses one set-based query per company for the as-of state (R11), not one query per member.

## R14. Rates: editing and history (FR-024, FR-025)

**Decision**:
- A rate change is a **new row** with a new effective date. The UI never edits amount columns in place.
- A trigger rejects updates to `total_premium`, `company_premium`, `employee_premium`, `class_code`, `coverage_band`, `dependent_band`, `effective_date` or `company_number` on any `premium_rates` row referenced by a FINAL billing line. `active` and `notes` can still change.
- Rate rows are created as a set of four tiers for a class, and the API refuses a set with a tier missing.
- **A class is assignable** (FR-022) only when all four tiers have an active **standard** rate. Company rates alone do not count, so every company can always be priced.

**Initial rate card**: the Access file supplied is schema-only, so it holds no rate values. The standard rates for A, B and C must come from the client. They load from `deploy/db/seed/premium_rates_standard.csv`, which is a **dependency**. Until it is loaded, members can be migrated but not billed, and classes A, B and C are assignable only once their rates exist. The migration therefore loads classes before rates, and the FR-022 check does not apply to migrated members.

## R15. Onboarding and offboarding (FR-017, FR-019)

**Onboarding**: one transaction, run by a super admin.
1. Insert `bhi.company`.
2. Optionally add the company to a client group.
3. Create one `ROLE_CLIENT_ADMIN` user with a temporary password and `must_change_password = true`, using the existing temporary-password flow.
4. Write the audit entry.

A duplicate company number fails on the primary key and returns `409`. Nothing else is created, and no DDL is involved, which meets SC-002 easily.

**Offboarding**:
- Set `company.active = false` and deactivate the company's admin users.
- The lookup and billing ignore inactive companies.
- Data stays readable to super admins, support and auditors.
- Writes to an inactive company's rows are refused in code, and an RLS `WITH CHECK` policy requires an active company for company-scoped writes.

## R16. Moving the existing data (FR-037 to FR-048)

**Decision**:
- A one-off command, `migrate-legacy`, built as a second esbuild entry (`dist/migrate-legacy.mjs`) and run as `bhi_owner`.
- It runs in **one transaction** and has a `--dry-run` mode that rolls back and prints only the report.
- Steps:
  1. Load classes A, B, C (names from `deploy/db/seed/classes.csv`).
  2. For each company in `public.companies`: insert `bhi.company`, and create an `import_batch` (`source_alias = LEGACY_MIGRATION`, a platform-wide unique `source_file` such as `LEGACY-BF-20261001`, and a new `source_ordinal`).
  3. Create the client group "Beharry" with the six companies, and scope the existing group admins to it.
  4. Map members, dependents and beneficiaries using [data-model.md](data-model.md#legacy-to-bhi-column-mapping). Write `legacy_key_map`, `member_class_history` (recorded at the member's `created_at`) and `enrollment_status_history` (for every inactive record, dated as in FR-038).
  5. Hold as exceptions in `bhi.import_exception`, linked to the company's batch:
     - missing ID type or class;
     - unknown class;
     - a value too long for its column;
     - duplicate `(id_type, id_number)` **anywhere on the platform**, which holds every record in the set (User Story 4, scenario 5).

     Each exception stores a JSON snapshot of the member, dependents and beneficiaries in `raw_row_summary`.
  6. Re-key the platform tables (R9).
  7. Write `import_reconciliation` rows for each company and table (linked through `import_batch_record`), and print the same counts with no personal data.
- Rehearsals use the demo seed or a de-identified copy (FR-048).

**Status and the imported "active" column**: `employee_members` has both the imported file's `active` / `inactive_*` columns and `member_status`, and today card access follows `member_status` only. To keep card access unchanged (SC-007), BHI `active` comes from `member_status`. Where the file said inactive but the status is ACTIVE, the file's date and reason are appended to `notes`.

## R17. HR fixing exceptions through bulk import (FR-041, FR-042)

**Decision**:
- `public.import_exception_resolutions (exception_id, resolved_at, resolved_by, member_id)` records fixes, because `import_exception` cannot gain a column.
- Bulk import, carrier layouts only:
  - checks every row against the BHI required columns and sizes;
  - creates an `import_batch` for the upload, and writes failing rows to `import_exception` under that batch's `source_file`;
  - matches existing members by `(id_type, id_number)`.
- A member row that matches an open exception (by ID type and number, or by ID number plus name for legacy exceptions with no ID type):
  - loads the member;
  - restores the held dependents and beneficiaries from the snapshot, unless the file supplies them;
  - resolves the exception.
- The commit runs **one transaction per company**. Today the import has no transaction (`admin.ts:1612-1662`).
- The legacy 8-column layout is withdrawn (`400 LAYOUT_WITHDRAWN`), because it cannot supply ID type or class.

## R18. Cut-over, sign-off and rollback

**Order**:
1. Apply the additive migrations: `bhi` schema, platform tables, new columns, roles. The old API still works.
2. Put up the maintenance page and take a backup.
3. Run `migrate-legacy --dry-run`, review it, then do the real run.
4. Review reconciliation.
5. Deploy the new API and portal.
6. Reopen traffic.
7. **At sign-off**, run `retire-legacy.sql`: move the four old tables to `legacy`, drop the old UUID columns and foreign keys, and grant `bhi_app` SELECT only on `legacy`.

**Rollback**: until step 6, redeploy the previous API. The old tables and columns are untouched. After reopening, rollback would need a reverse script, which is out of scope. The constitution's release-readiness gate requires the rollback to be rehearsed before cut-over.

**Duration**: expected under 10 minutes for about 5,000 members. It is measured in rehearsal.

## R19. Age-65 sweep

`sweepRetirementAge` runs in `ALL` scope as one query over `bhi.member`, selecting members with `active = true` and `date_of_birth <= cutoff`. For each, it:
- sets `active = false`, `inactive_date = today` and `inactive_reason = 'Aged out at 65'`;
- writes `enrollment_status_history` and `audit_logs`;
- revokes card sessions.

Members with no date of birth are returned in a "cannot check age" list for HR. Scheduling is unchanged.

## R20. Testing approach

- **Integration tests** use vitest against a real PostgreSQL **connected as `bhi_app`**. A superuser would bypass RLS and hide segregation bugs.
- **Structural test (SC-001)** compares `information_schema` and `pg_indexes` for `bhi` with a machine-readable copy of [contracts/bhi-schema.sql](contracts/bhi-schema.sql). It allows only D1 to D3, plus the RLS policies and triggers, which are not structure.
- **Segregation tests (SC-003)** check every admin route as a client admin, a group admin and an HR administrator against other companies' IDs, and expect the same 404 as for a missing record. RLS tests run raw `SELECT`s **without** a company filter as each scope, and expect only in-scope rows.
- **Billing tests (SC-005)** use a fixture month covering:
  - 0, 1, 2, 3 and 7 dependents;
  - an addition, a removal, a class change and a new dependent recorded before and after T;
  - a standard-rate company, a company-rate company and a CompanyBillingRule company.

  Expected lines come from a hand-calculated table in the test, and must match to the cent.
- **Lookup tests (SC-009)**: the four pre-verification response bodies are identical apart from `verificationId` and `maskedDestination`, and response-time medians over 200 runs differ by less than 50 ms.
- `scripts/rbac-test.mjs` is extended for the new roles and routes.
