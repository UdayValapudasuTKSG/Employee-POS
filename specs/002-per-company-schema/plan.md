# Implementation Plan: Multi-Company BHI Enrollment and Monthly Billing on One Shared Database

**Branch**: `002-per-company-schema` | **Date**: 2026-09-29 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-per-company-schema/spec.md`

## Summary

Every client company's enrollment data moves into the 18 tables of the client's BHI Enrollment Database. The tables are held once, in a dedicated `bhi` schema of the existing PostgreSQL database, and shared by all companies. The only change to the client's tables is an optional `CompanyNumber` on `PremiumRates`, so rates can become company-specific.

How it works:

1. **Segregation** has two layers:
   - The API applies a role-based scope: super admin, group, company, or read-only all.
   - PostgreSQL row-level security enforces the same scope in the database, so a forgotten filter returns nothing.
2. **Premium and billing**:
   - Classes are shared by all companies.
   - Each class has four tiers, set by the number of active dependents (0, 1, 2, 3+).
   - A standard rate card applies today; company rates override it later.
   - Each company gets a monthly billing run, priced from the member's state as recorded at 00:00 on the 1st.
3. **Onboarding**: a super admin creates a company and one client admin. Client and group admins manage their own users.
4. **Migration**: a one-off, single-transaction command moves the current data. Incomplete records are held as exceptions for HR to fix through bulk import.
5. **Card lookup**: it searches every company, always gives the same response before verification, and after verification tells the employee to contact HR when their contact matches more than one company.

## Technical Context

**Language/Version**: TypeScript 5.x on Node.js 20+ (ESM), as today.

**Primary Dependencies**:
- API: Express 5, drizzle-orm 0.45 (`pgSchema`) with node-postgres, and zod generated by orval from `lib/api-spec/openapi.yaml`.
- Portal: React with react-query hooks from `lib/api-client-react`.
- No new runtime dependency.

**Storage**: PostgreSQL 15+ (16 in Docker and Replit). One database with three schemas:
- `bhi`: the 18 tables, with row-level security.
- `public`: platform tables.
- `legacy`: retired tables, after sign-off.

There are two roles, `bhi_app` and `bhi_owner` ([research R5](research.md#r5-database-roles-and-grants)).

**Testing**:
- vitest integration tests against a real PostgreSQL, connected as `bhi_app`.
- The HTTP acceptance script `scripts/rbac-test.mjs`.
- A billing fixture test with hand-calculated expected lines.
- The portal has no automated tests, and is checked with the quickstart.

**Target Platform**: Linux server behind nginx (Azure VM, GCP) or Docker Compose locally, using the existing deploy scripts.

**Project Type**: Web application (API plus React admin and employee portal) in a pnpm monorepo.

**Performance Goals**:
- Onboarding: under 5 minutes (SC-002), expected under 1 second.
- New class with its four rates: under 5 minutes (SC-008).
- Monthly bill for all companies, about 5,000 members: under 5 minutes (SC-011).
- `/v1/lookup`: at least 800 ms for every outcome, with medians within 50 ms of each other over 200 runs (SC-009).
- Legacy migration: under 10 minutes for about 5,000 members, measured in rehearsal.

**Constraints**:
- No hard deletes: the app role has no DELETE right on `bhi`, and audit is insert-only (Principle III).
- A query with no scope set returns no rows.
- The migration is all-or-nothing, with a dry run.
- Rehearsals use synthetic or de-identified data only.
- No personal data in logs or reports.

**Scale/Scope**:
- About 4,970 members in 6 Beharry companies today, with more policyholders to come.
- About 35 admin routes changed or added, 8 employee routes changed, and about 12 portal pages changed or added.

**Dependencies on the client** (none blocks planning; the first blocks finalising a bill):
1. The actual standard rate card for classes A, B and C. The Access file supplied is schema-only ([R14](research.md#r14-rates-editing-and-history-fr-024-fr-025)).
2. The names of classes A, B and C.
3. Whether the Access file sets a precision for its "Decimal number" fields ([R3](research.md#r3-type-mapping)).
4. Confirmation that CompanyBillingRule percentages override the rate card's split (spec FR-032).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design.*

| Principle / gate | Assessment | Status |
|---|---|---|
| **I. Zero disclosure before verification** | `/v1/lookup` gives one response and one minimum time for every outcome. Multi-record choice, the multi-company message and delivery failures all move after verification or out of the response ([R10](research.md#r10-employee-card-lookup-across-companies-fr-016)). This fixes today's pre-verification `404`, `SELECT` and `503` replies. Out-of-scope records return the same 404 as missing ones. A duplicate ID across companies returns a message that does not name the other company (FR-007). | PASS (improves) |
| **II. Layered identity assurance** | OTP and card-token rules are unchanged. Not addressed and not made worse: the lookup has no second non-broadcast factor, and admin sign-in does not use Entra ID. New client admins use the existing temporary-password, must-change flow. | PASS, existing gaps noted |
| **III. Archive-only records, immutable audit** | Records deactivate with a reason and are never deleted. `bhi_app` has no DELETE on `bhi`, and INSERT/SELECT only on `audit_logs`. Offboarding deactivates. Billing recalculation supersedes instead of deleting. FINAL runs and used rates are frozen by triggers. Old tables are archived to `legacy`. The R3 cascade exists in the DDL, but no application role can trigger it. | PASS (improves) |
| **IV. Data residency and lawful processing** | Data stays in the same database and location. What is stored changes: fields are dropped, exception snapshots hold personal data, lookup alerts hold masked contacts, and billing lines hold names and premiums. More policyholders means more data subjects. This triggers the **data protection review gate**. | PASS, gate required |
| **V. Usable at the point of care** | Card fields are unchanged, and the name lines look the same. Offline and revocation behaviour is unchanged, and deactivation revokes card sessions. | PASS |
| **VI. Measurable NFRs** | Every target above has a number and a measurement point (quickstart §1–§9). | PASS |
| **VII. Observability without exposure** | The migration report and billing summaries carry counts and totals, not personal data. Exception details stay in the database, behind RLS. | PASS |
| **Security, Access**: "administrator visibility is scoped to approved companies" | Enforced by role scope and RLS. Group admins are limited to their group, and only super admins see everything (FR-012, FR-013). | PASS |
| **Security review gate** | Required: this changes the disclosure surface, the verification flow, admin roles and user management, database grants and RLS. | Gate before merge |
| **Testing gate** | Negative cases planned: cross-company access by each role, a scope-less query returning 0 rows, client admin privilege escalation, last-admin removal, decoy lookup, delete attempts as `bhi_app`, finalised bill edits, used-rate edits ([R20](research.md#r20-testing-approach)). | PASS |
| **No production data outside production** | Rehearsals use the seed or a de-identified copy (FR-048). | PASS |
| **Release readiness** | A cut-over runbook and a rehearsed rollback are required before go-live ([R18](research.md#r18-cut-over-sign-off-and-rollback)). | Gate before cut-over |
| **Constitution TODO(DATABASE_ENGINE)** | This design relies on PostgreSQL features (RLS, `NULLS NOT DISTINCT`, transaction-local settings). The IT Manager should close this TODO in favour of PostgreSQL. | NOTE |

**Structure decision**:
- Keep the monorepo layout.
- BHI tables go in `lib/db/src/schema/bhi/`, so the API and the migration command share one definition.
- Database changes follow the project's existing hand-written, re-runnable SQL migrations in `deploy/db/migrations/`, which the local, Docker and Azure runners already apply in order. They now run as `bhi_owner`.
- Billing logic is split into pure pricing, which is unit-tested, and database-facing as-of and run code.

## Delivery Order

Each slice can be tested on its own:

1. **US1**: the `bhi` schema, RLS, roles and grants, and the structural test (SC-001).
2. **US2 + US3**: scopes and `withScope`, the new roles, client groups, onboarding, user management, admin routes moved onto `bhi`, and segregation tests (SC-002, SC-003, SC-010). The card lookup rework (SC-009).
3. **US4**: the migration command, platform re-keying, import exceptions, the bulk import rework, the retirement sweep, the portal member screens, and the cut-over runbook (SC-004, SC-006, SC-007).
4. **US5**: classes, rates and billing rules, API and pages (SC-008).
5. **US6**: billing as-of, pricing, runs, pages and export (SC-005, SC-011).

Production cut-over needs slices 1–3. Slices 4–5 can follow, and are needed before the first bill. Billing also needs the client's rate card.

## Complexity Tracking

| Addition | Why needed | Simpler alternative rejected because |
|---|---|---|
| Row-level security on all `bhi` tables | FR-011: segregation must not depend on every query's filter; SC-003 | Code-only filtering fails FR-011; per-company views must be rebuilt at every onboarding |
| Second database role (`bhi_owner`) | RLS and no-delete only bind a non-owner, non-superuser role; the audit store needs write-once credentials (Principle III) | One role that owns the tables would bypass RLS and could delete |
| `member_class_history` platform table | Billing needs a member's class at 00:00 on the 1st (FR-029); the BHI model keeps only the current class | A snapshot job on the 1st misprices a month if it runs late; adding a column or table to the BHI model breaks SC-001 |
| `import_batch` and `import_batch_record` | The 10 import tables must stay as given, yet HR must see only their company's rows (FR-009, answer 3B) | Adding CompanyNumber to the 10 tables was declined |
| Superseding draft runs instead of replacing lines | No delete right for the app (Principle III) | Deleting and re-inserting lines needs DELETE, and loses the record of earlier drafts |
